# W6 Lab. CSR SpMV: Profiling the Impact of Memory Access Locality

## 1. Introduction

This project studies the performance effect of memory-access locality in a
Compressed Sparse Row (CSR) sparse matrix-vector multiplication (SpMV)
workload.

The benchmark runs the same mathematical operation in two layouts:

- `local`: input-vector accesses follow the logical column order.
- `permuted`: the same logical values are placed at permuted physical
  positions, producing less predictable input-vector accesses.

The project measures elapsed kernel time and collects hardware-performance
information using both an in-program PMU implementation and Linux `perf`.
Correctness is checked for every run so that performance results are only
reported when the computed output matches an independently generated oracle.

The experiments were run on the system documented in
`log/0_system_info/`. Important characteristics are:

- **CPU:** Intel Xeon Gold 6526Y
- **Architecture:** x86-64
- **CPUs:** 64 logical CPUs, two sockets, 16 cores per socket, two threads
  per core
- **Caches:** 1.5 MiB L1 data cache across 32 instances, 64 MiB L2 cache
  across 32 instances, and 75 MiB L3 cache across two instances
- **Operating system:** Linux 5.14.0-611.5.1.el9_7.x86_64

## 4. Workload

The core operation is Compressed Sparse Row (CSR) sparse matrix-vector multiplication (SpMV).

```cpp
#if defined(__GNUC__) || defined(__clang__)
__attribute__((noinline))
#endif
static void csr_spmv(const std::vector<std::size_t>& rp,
                     const std::vector<std::uint32_t>& ci,
                     const std::vector<double>& val,
                     const std::vector<double>& x,
                     std::vector<double>& y) {
    for (std::size_t r = 0; r + 1 < rp.size(); ++r) {
        double s = 0.0;

        for (std::size_t k = rp[r]; k < rp[r + 1]; ++k)
            s += val[k] * x[ci[k]];

        y[r] = s;
    }
}
```

`rp` stores the beginning and end of each row. `ci` stores the column index
for each nonzero, and `val` stores the corresponding matrix value. The matrix
arrays are traversed sequentially in CSR order. The experiment primarily
changes the access pattern for `x[ci[k]]`.

The default workload uses:

```text
rows       = 65536
ncols      = rows * 4  = 262144
nnz/row    = 8
nnz        = 524288
iterations = 500
```

The setup uses the selected pattern in both the input vector and the CSR
column indices:

```cpp
const std::size_t physical =
    (pattern == "local") ? logical : permutation(logical, ncols);

col_idx[k] = static_cast<std::uint32_t>(physical);
```

### 4.1 Local Layout

For `--pattern local`, the physical position equals the logical position:

```cpp
physical = logical;
```

Nearby logical columns therefore access nearby elements of the contiguous
input vector:

```text
x[0], x[1], x[2], x[3], ...
```

### 4.2 Permuted Layout

For `--pattern permuted`, the physical position is generated by a bijective
permutation:

```cpp
physical = permutation(logical, ncols);
```

The input vector is still a contiguous `std::vector<double>`, but the SpMV
kernel accesses it through a scattered index order:

```text
x[17], x[4], x[29], x[8], ...
```

The logical result remains the same. Only the physical order of input-vector
accesses changes, allowing locality to be studied independently of
mathematical correctness.

## 5. Profiling

The benchmark separates setup from the measured kernel:

```cpp
// ==================== SETUP START ====================
// Matrix allocation, input generation, CSR construction,
// and oracle generation.
// ===================== SETUP END =====================

// ==================== KERNEL START ===================
const auto start = std::chrono::steady_clock::now();

for (std::size_t i = 0; i < iters; ++i)
    csr_spmv(row_ptr, col_idx, values, x, y);

const auto stop = std::chrono::steady_clock::now();
// ===================== KERNEL END ====================
```

The reported `timed_kernel_s` and `ns_per_nnz` values cover only the repeated
SpMV calls. Setup, warm-up, correctness checking, and output formatting are
outside that timing interval.

The benchmark first performs a warm-up and compares the result with the
oracle. It repeats the comparison after the timed loop:

```cpp
if (y != expected)
    throw std::runtime_error("FAIL: timed output differs from oracle");
```

This prevents an invalid computation from being reported as a successful
performance result.

## 6. PMU (Performance Monitoring Unit)

`KernelPmu` is a C++ class in
`src/CSR_SpMV_benchmark_kernel_PMU.cpp`. The PMU-enabled executable uses this
class to collect hardware counters only around the timed SpMV loop. It opens a
grouped set of Linux hardware events:

```cpp
constexpr std::uint64_t events[3] = {
    PERF_COUNT_HW_CPU_CYCLES,
    PERF_COUNT_HW_INSTRUCTIONS,
    PERF_COUNT_HW_CACHE_MISSES
};
```

The lifecycle is:

```cpp
KernelPmu pmu(request_pmu);
pmu.prepare();
pmu.start();

// timed SpMV loop

pmu.stop();
pmu.report();
```

`prepare()` opens the counters but does not start counting. `start()` resets
and enables the group immediately before the kernel. `stop()` disables and
reads the group immediately afterward. `report()` prints the counter values,
IPC, and running fraction.

The PMU output is scoped to user-space execution of the timed loop:

```text
PMU_SCOPE=timed_spmv_loop_user_only
```

The default PMU experiment uses `ncols = rows * 4` and produces logs under
`log/3_pmu_col4/`. The col16 experiment is built with
`-DNCOLS_MULTIPLIER=16` and produces logs under `log/4_pmu_col16/`.


## 7. Linux `perf` Tool

The runner uses `perf stat` to collect process-level event counts:

```bash
$ perf stat -r 3 -e cycles,instructions,cache-misses -- \
    build/spmv_profile --pattern local \
    --rows 65536 --nnz-per-row 8 --iters 500
```

These values cover the launched process, so they can include setup and
verification in addition to the kernel. They are useful for broad comparison,
but they do not have the same narrow scope as `KernelPmu`.

The runner also records sampled call stacks:

```bash
$ perf record -g -o perf/perf_record_local.data -- \
    build/spmv_profile --pattern local \
    --rows 65536 --nnz-per-row 8 --iters 500
```

The raw recording is inspected with:

```bash
$ perf report --stdio -i perf/perf_record_local.data
```

The text reports are saved under `log/6_perf_report/`. The raw `.data` files
under `perf/` are binary inputs for `perf report`

## 8. Result

The values below are representative results recorded in `log/`. Hardware
performance results vary with CPU frequency, system load, process placement,
and other activity on the machine.

### 8.1 Local vs Permuted

Both layouts pass correctness with the same checksum:

```text
local:    checksum=727476.546875
permuted: checksum=727476.546875
```

The baseline timing logs show a substantial locality effect:

| Pattern | Timed kernel | ns/nonzero |
|---|---:|---:|
| Local | 0.163229 s | 0.622670 |
| Permuted | 0.389199 s | 1.484677 |

The permuted layout is approximately 2.4 times slower in this run. The
permuted case uses the same mathematical values, but its `x[ci[k]]` accesses
are less sequential.

The `perf stat` logs show the same trend:

| Pattern | Cycles | Instructions | IPC | Cache misses |
|---|---:|---:|---:|---:|
| Local | 767,942,142 | 2,363,753,478 | 3.08 | 133,411 |
| Permuted | 1,559,785,588 | 2,365,090,291 | 1.52 | 217,120 |

The instruction counts are nearly identical because the algorithm performs
the same number of arithmetic and loop operations. The permuted case uses
roughly twice as many cycles and has approximately half the IPC, indicating
that the irregular memory accesses limit execution throughput.

The in-program PMU logs provide the same interpretation with a tighter kernel
scope:

| Pattern | PMU cycles | PMU instructions | IPC | Cache misses |
|---|---:|---:|---:|---:|
| Local | 658,793,136 | 2,261,009,402 | 3.43 | 7,127 |
| Permuted | 1,321,122,243 | 2,261,009,573 | 1.71 | 323 |

The cache-miss event is CPU-dependent and should not be interpreted as a
direct measurement of DRAM traffic. The main consistent signal is the much
higher cycle count and lower IPC for the permuted access pattern.

### 8.2 Col4 vs Col16 Input Vectors

The col4 configuration uses:

```text
ncols = rows * 4  = 262144
```

The col16 configuration uses:

```text
ncols = rows * 16 = 1048576
```

The nonzero count stays fixed at `524288`, so changing the column multiplier
increases the input-vector footprint without increasing the arithmetic work.

Representative PMU results are:

| Configuration | Pattern | Timed kernel | ns/nonzero | PMU cycles | PMU cache misses |
|---|---|---:|---:|---:|---:|
| Col4 | Local | 0.169460 s | 0.646439 | 658,793,136 | 7,127 |
| Col4 | Permuted | 0.339831 s | 1.296351 | 1,321,122,243 | 323 |
| Col16 | Local | 0.187892 s | 0.716752 | 730,180,458 | 60,940 |
| Col16 | Permuted | 0.512776 s | 1.956086 | 1,993,731,639 | 8,990 |

The PMU cache-miss values require careful interpretation. In this run, the
local col4 case reported more PMU cache misses than the permuted col4 case.
This does not contradict the timing results. `PERF_COUNT_HW_CACHE_MISSES` is
CPU-dependent and does not necessarily count every cache miss or measure DRAM
traffic directly. Cache state, hardware prefetching, NUMA placement, and the
specific processor event mapping can all affect the result. The stronger
signals are the substantially higher cycle count and lower IPC for the
permuted layout. The cache-miss column should therefore be treated as
supporting evidence rather than as a direct measure of memory latency.

The larger vector increases the physical footprint by four times while the
number of nonzeros remains unchanged. That makes it more difficult for the
working set to remain close to the core.

The CPU information in
`log/0_system_info/cpu_info.log` reports:

```text
L1d cache: 1.5 MiB (32 instances)
L2 cache:  64 MiB (32 instances)
L3 cache:  75 MiB (2 instances)
```

The col4 input vector alone contains approximately:

```text
262144 * 8 bytes = 2 MiB
```

The col16 input vector contains approximately:

```text
1048576 * 8 bytes = 8 MiB
```

These sizes do not describe the entire working set, because the CSR value and
index arrays and output vector also consume memory. Nevertheless, the larger
col16 input vector increases the amount of data that can be touched by
permuted accesses. This is consistent with the observed increase in cycles,
kernel time, and `ns_per_nnz`, especially for the permuted pattern.

### 8.3 Overall Result

The experiments show three main results:

1. Both layouts compute the same result. In the col4 runs, both report
  `checksum=727476.546875`; in the col16 runs, both report
  `checksum=727541.664062`. This confirms that the comparison changes memory
  layout without changing the computed result.
2. The permuted layout is slower than the local layout. For col4, the baseline
  kernel time increases from `0.163229 s` to `0.389199 s`, while
  `ns_per_nnz` increases from `0.622670` to `1.484677`. The PMU results also
  show cycles increasing from `658,793,136` to `1,321,122,243` and IPC
  decreasing from `3.43` to `1.71`.
3. Increasing the column count from col4 to col16 increases the input-vector
  footprint while keeping `nnz=524288` fixed. For the permuted layout,
  `ns_per_nnz` increases from `1.296351` to `1.956086`, and PMU cycles
  increase from `1,321,122,243` to `1,993,731,639`. This supports the
  conclusion that the larger working set makes irregular accesses more
  expensive.

The timing benchmark, in-program PMU, `perf stat`, and `perf report` provide
different views of the same behavior. They should not be expected to produce
identical absolute counts because they measure different scopes and use
different sampling or counting mechanisms.

## 9. Conclusion

The project demonstrates how two CSR SpMV executions can be mathematically
equivalent while having different performance because of input-vector memory
locality.

The local layout preserves a sequential access pattern for `x[ci[k]]`. The
permuted layout accesses the same vector through scattered physical indices,
which increases cycles and reduces IPC in the recorded experiments.

The col16 experiment further shows how increasing the input-vector footprint
can amplify memory-system effects without changing the number of nonzeros or
the amount of arithmetic performed by the kernel.

Using `make` for builds and `run.sh` for execution makes the experiments
repeatable. The generated logs preserve the commands, correctness results,
timings, PMU measurements, and Linux `perf` reports needed to inspect and
compare the runs.
